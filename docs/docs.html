Documentation

webhookr is a self-hosted webhook runner. Point a GitHub (or generic) webhook at it, and when a webhook fires, webhookr does a git pull on the configured branch and runs your deploy command, logging everything so you can tail it later.

Install & updating

$ curl -fsSL https://github.com/kodin00/webhookr/releases/latest/download/install.sh | sh

This installs the Linux x86_64 binary to /usr/local/bin/webhookr (override with WEBHOOKR_INSTALL_DIR), verifies its checksum, and sets up a webhookr systemd service that starts on boot and restarts on failure.

Updating

From the app: Settings → Version → Update and restart in the web UI, or Update webhookr (v) in the TUI. From a shell:

webhookr version       # what is running, and what is published
webhookr update        # replace this binary with the published build

Re-running the install one-liner also works. It overwrites the binary, rewrites the systemd unit, and restarts the service. Run it from the same account as before: the unit's User= is set to whoever invoked the script, and a different $HOME means a different config.json (every project appears to vanish). releases/latest/download serves whatever latest points at right now, so if you push and install within a couple of minutes you can silently reinstall the old build. webhookr version is the check.

Self-update needs write access to the installed binary. The daemon does not run as root, so a root-owned binary must be updated via the install one-liner (which uses sudo). Updating from the web UI or serve exits the process on purpose so the service manager starts the new binary. Under systemd it comes back; in a terminal it does not.

$ webhookr version
running:   0.2.1 (73deef9)
published: 0.2.1 (73deef9) (up to date)

(local build) instead of a commit means the binary was built from a checkout rather than installed from a release.

Building from source

Prerequisites:

  • Rust (via mise). .mise.toml pins the toolchain.
  • Git, plus Docker with the Compose plugin for Compose presets.
  • An installed cloudflared binary or Docker when using Cloudflare Tunnel.
mise exec -- cargo build --release

The binary is target/release/webhookr.

How it works

  • Each project maps a URL slug (/hooks/<id>) to a Git checkout plus a deployment preset or custom shell command.
  • Incoming webhooks are authenticated against a per-project secret, then git fetch / checkout / pull runs before the command.
  • Projects and the listen address live in one JSON config file, shared between the daemon and the management CLI/TUI.
  • Run history and per-run logs are written to a separate state directory. Logs stream to disk as commands produce them, so a long docker compose build can be followed while it runs.
  • Each run records what triggered it (push by <user>, merge by <user>, workflow_dispatch by <user>, webhook, web UI, or cli), shown on run pages, dashboard cards, and in Telegram messages.
  • Any past successful run can be rolled back: the recorded commit is checked out detached and the preset re-run. Forward deploys dump the project's database (when one is configured) before touching git, so a rollback restores data as well as code.
  • Only one run per project at a time. A trigger arriving while that project is already deploying is refused rather than queued, so two pushes cannot race git pull on the same checkout.

Quick start

# 1. Register a project (prompts for anything you don't pass)
webhookr add \
  --name "My Site" \
  --path /srv/my-site \
  --repository https://github.com/me/my-site.git \
  --branch main \
  --preset compose_build \
  --compose-file compose.production.yaml

# 2. Get the secret + webhook URL (printed on add, or via:)
webhookr key --id my-site

# 3. Start the daemon (systemd recommended for production)
webhookr serve
# ...or launch the interactive TUI
webhookr

webhookr add prints the generated secret once. Use webhookr key --id <id> to show it again, and --rotate to roll it.

Deployment presets

PresetBehavior
compose_builddocker compose -f <file> up -d --build --remove-orphans
compose_pullPull images, then run Compose detached with orphan cleanup.
compose_upRun Compose detached without forcing a pull or rebuild.

Use --compose-profile <name> more than once to enable Compose profiles. Compose files must be relative to the checkout and cannot use .. to escape it.

Private repositories

Set an access token on the project (web UI, Source section) to clone and pull private repos over HTTPS. Use a GitHub personal access token with read access to the repository. It is handed to git through a credential helper that reads an environment variable, so it never appears in the process list and is never written into the checkout's .git/config.

If --repository is set and the project path does not exist, the first update clones that branch into the path. Later updates fetch, check out, and fast-forward the same branch.

Multi-branch deploys

A project can deploy more than one branch from the same checkout. The project's own branch is the primary. Each extra branch carries its own preset or command, compose file, profiles, env file, compose project name, merge sources and database settings. Path, repository, secret, credentials and triggers are shared, and so is the webhook URL.

A delivery for a branch checks that branch out in the shared worktree, pulls it, and deploys with that branch's settings. Runs on one project never overlap, so the branches take turns on the worktree.

# develop is the primary branch (custom command); add sandbox alongside it
webhookr branch add myapp sandbox \
  --preset compose_build \
  --compose-file docker-compose.sandbox.yml \
  --env-file .env.sandbox
webhookr run --id myapp --branch sandbox   # manual run of one branch
  • Env file. Compose presets pass it as --env-file. Custom commands get its KEY=VALUE pairs in their environment, along with WEBHOOKR_BRANCH, WEBHOOKR_PROJECT_ID, WEBHOOKR_ENV_FILE and WEBHOOKR_COMPOSE_PROJECT.
  • Compose project name. An extra branch deploys under -p <id>-<branch> unless you set one. Without a separate name, --remove-orphans on one branch would tear down the other branch's containers. The primary keeps Compose's default name unless you set one.
  • Token-mode senders pick a branch with POST /hooks/<id>?branch=<name>. Without it they deploy the primary branch.
  • Redeploy without pulling works for any branch. If the worktree is on another branch, webhookr checks out that branch's local ref, without fetching, so you get the code it last pulled. A branch that has never been pulled into the checkout needs one Pull & deploy first. After a rollback, redeploying the same branch keeps the rolled-back commit. The project page shows which branch the worktree is on.
  • Bind mounts. A stack that bind-mounts the source sees whichever branch is checked out last.

Extra branches are managed in the web UI (Extra branches on the project form), or with webhookr branch list|add|remove|set. The TUI shows them but doesn't edit them.

Rollback & database backups

Any past successful run can be redeployed as a rollback. webhookr fetches, checks out the commit that run deployed (git checkout --detach <sha>, never touching the branch) and re-runs the project's normal deploy preset. When the project's database has backups on, the data from just before that run is restored too.

A rollback is operator-only: web UI, CLI, or TUI. A webhook can never start one. Afterwards the checkout sits detached at the old commit, and the next push-triggered deploy checks the branch back out and fast-forwards, so a rollback is transient by design. A dirty working tree is refused (git's own error shows in the run log). webhookr never discards uncommitted work.

From the web UI

Every run page for a success run with a recorded commit has a Rollback to this run button. It opens a confirm page showing the commit, the preset that will run, and the database dump that will be restored, or a note that no dump was recorded and the rollback will be code-only. Confirming starts a new run.

From the CLI and TUI

webhookr rollback <id>                    # most recent successful run
webhookr rollback <id> --to <run-or-sha>  # a specific run id or commit sha
webhookr rollback <id> --no-db --yes      # code only, no prompt

In the TUI, press r while viewing a run to roll back to it.

Database backups

Backups are the data half of a rollback, configured per project in the database section:

SettingWhat it does
Mode

auto (default): detect the database by asking docker compose config which services run Postgres, PostGIS, MySQL, or MariaDB. The file probed is the project's database compose file: the one picked on the project form (a file picker), defaulting to the preset's compose file for compose deployments. A custom-command project must pick one, or detection answers none.

manual: override what detection got wrong. The engine (kind) and compose service you set are used verbatim, and any you leave blank are read from the database compose file.

off: no backups, rollbacks are code-only.
BackupsOn by default. Every forward deploy dumps the database before touching git, and a failed dump fails the deploy before any code change.
KeepHow many dumps to keep per project (default 5). The oldest are pruned once a new one lands.

Dumps live under the state dir in backups/<project>/. Credentials resolve inside the container ($POSTGRES_USER, $MYSQL_ROOT_PASSWORD, …) and are never stored or logged by webhookr. The project page shows the detected database, every saved dump with its date and size, and a Back up now button for a manual dump outside any deploy (webhookr backup <ID> does the same from the shell; either is how you seed history for a project whose deploys predate backups). A manual dump counts against keep like any other.

A rollback with a database first takes a pre-rollback safety dump of the current state, then restores the dump taken immediately before the run being undone, which is exactly the data state of the previously-good deploy. Postgres restores by dropping and recreating the public schema; MySQL and MariaDB by dropping and recreating the app database. If no dump was recorded for that run, the rollback is offered as code-only and says so. Mongo and Redis services can appear in a compose file but are not backed up in v1, so those projects roll back code-only.

Caveats

  • Auto-detection covers compose-managed databases only. Dumps and restores run through the database's own compose service, so one that auto-detection misses must be named with manual, and a fully external managed database is out of scope.
  • Shared databases are not coordinated. Two projects deploying against one database take independent dumps and can restore over each other's data.

Web admin UI

An optional browser dashboard that does everything the TUI does: add, edit and remove projects, reveal and rotate secrets, trigger deploys, watch run logs stream live, and configure the Cloudflare Tunnel, with web forms instead of a terminal wizard.

It has no login. Anyone who can reach it can set a project's deploy command and run it as the daemon's user, and can replace the webhookr binary. Put Cloudflare Access (or an equivalent) in front of it before exposing it, and set User= in the systemd unit so that user is not root.

Off by default. Turn it on with:

webhookr web enable --addr 127.0.0.1:9001
sudo systemctl restart webhookr

The UI runs inside the same webhookr serve process as the webhook listener. Its port serves both surfaces: the dashboard at /, and webhooks at /webhook/<id> (with /hooks/<id> kept as an alias), so one hostname is enough for everything.

Reaching it

The default bind is 127.0.0.1, which still works through a Cloudflare Tunnel: cloudflared runs on the same host and connects to http://127.0.0.1:<port>. Binding to 0.0.0.0 would additionally expose the panel on the LAN and the server's public IP, where Access cannot protect it.

To publish it on one hostname, provision the tunnel with only an admin hostname. The admin port already serves webhooks too:

export CLOUDFLARE_API_TOKEN='scoped-token'
webhookr cloudflare --admin-hostname deploy.example.com
sudo systemctl restart webhookr

That gives you https://deploy.example.com for the dashboard and https://deploy.example.com/webhook/<id> for GitHub.

Access needs a path exception. GitHub cannot complete an Access login, so a policy covering the whole hostname will silently break every delivery. In the Access application for deploy.example.com, add a Bypass policy for the path /webhook/* (and /hooks/* if you use the alias) ahead of your normal policy. Those paths stay protected by the per-project HMAC/token check.

To keep them apart, pass both hostnames and Access only the admin host:

webhookr cloudflare --hostname hooks.example.com --admin-hostname deploy.example.com

For a quick look without persisting anything or exposing it at all:

webhookr serve --web --web-port 9001    # then browse http://127.0.0.1:9001

GitHub webhook setup & triggers

In your repo: Settings → Webhooks → Add webhook:

  • Payload URL: http://<vps-ip>:9000/hooks/<id>
  • Content type: application/json
  • Secret: the project's secret (webhookr key --id <id>)

webhookr verifies the X-Hub-Signature-256 header against the project's secret before running anything.

Deployment triggers

Deliveries are branch-aware: a push only triggers when it targets the project's configured branch, and a merge only when it lands on that branch. A push to some other branch no longer causes a redundant deploy of the configured one.

By default a project deploys on every such delivery. Narrow it per project by picking which events trigger a deploy:

  • Push: a push to the configured branch, including the merge commit pushed after a PR merge.
  • Merge: a pull_request event that was closed and merged. Needs the pull_request event enabled in your GitHub webhook settings (the default push-only webhook will not fire it).

Leave both unticked to keep the default (every delivery). A ping delivery never triggers a deploy. If both are selected, a PR merge fires two deliveries; the second is refused by webhookr's one-run-at-a-time lock, so only one deploy starts.

Merges can be narrowed further by source branch: Merge from branches lists the PR head branches whose merges may trigger a deploy. For example, set it to develop and only merges from develop deploy. Empty (the default) accepts any merge. The push trigger is not affected by it.

Set triggers in any of the three surfaces: the web admin UI (Deployment triggers on the project form), the CLI (webhookr add --trigger-event push --trigger-event merge --merge-source develop, or omit on edit to leave unchanged), or the TUI wizard's Triggers step (Tab edits the branch list).

GitHub commit status

webhookr can report each deploy back to GitHub as a commit status, so the commit you pushed shows the pending dot, green check or red X on the repository page, the commits list and any pull request that contains it. Details opens that run's log. Off by default; turn it on per project in the web admin UI under GitHub commit status:

SettingWhat it does
Report deploy resultsThe master switch for this project.
Status tokenA token that can write commit statuses. Leave blank to reuse the project's access token.
ContextThe label GitHub shows beside the status. Defaults to webhookr/<id>.

The token needs repo:status on a classic personal access token, or Commit statuses: write on a fine-grained one scoped to the single repository. repo:status is deliberately narrow: it grants no access to the repository's code. A fine-grained token scoped only to read contents (the right scope for cloning) cannot write statuses, which is why this is a separate field. When one token covers both, leave it blank and the access token is used. The default context is per project, so two webhookr projects deploying from one repository do not overwrite each other's indicator.

What gets posted: pending when the deploy starts; success when it finishes (e.g. deployed in 47s); failure when it exits non-zero (described with the last line of its output); error when the source could not be fetched at all. The status lands on the commit named in the push payload when the push was to the project's branch, and on git rev-parse HEAD otherwise, including manual deploys, so a redeploy after a fix clears a stale red X. If the pull moves HEAD past the announced commit, both get the final status so nothing is left pending forever. A push that arrives while a project is already deploying is refused and gets a terminal error; the in-flight run's own git pull picks that commit up anyway and supersedes the error.

Posting a status can never fail or delay a deploy. Anything that goes wrong is written into the run log as a # github status: line and otherwise ignored.

The Details link points at /runs/<run-id> on the admin UI, using the tunnel's admin hostname. With only a loopback address the link is omitted rather than pointing at 127.0.0.1; the webhook hostname is never used for it. Following the link hits Cloudflare Access normally and needs no bypass policy.

GitHub Enterprise

The API host is derived from the repository URL, with nothing to configure: a github.com remote uses api.github.com, and any other host is treated as GitHub Enterprise Server at https://<host>/api/v3.

Telegram notifications

webhookr can post each deploy to a Telegram chat through a bot you own: 🚀 when a run starts, ✅ when it succeeds, ❌ when it fails, quoting the tail of the run log on a failure. Off by default, and global: one bot and one chat for every project, configured under Settings in the web admin UI.

SettingWhat it does
Notify a Telegram chat about deploysThe master switch.
Bot tokenA token from @BotFather. Stored like the other secrets: the form never echoes it back, blank keeps the stored one.
Chat idThe chat to post to. Group chats have negative ids; @channelname also works.

To find a group's chat id: create the bot with @BotFather, add it to the group, send any message in the group, then open https://api.telegram.org/bot<token>/getUpdates and read message.chat.id. It will start with -100.

The started message carries the project, run, commit, and trigger (push by alice, merge by alice, web UI, …). The finished messages carry the duration and result (or the error and tail of the log on failure), with the trigger beside the commit. When the admin UI has a public hostname, each message ends with a link to that run's log page; with only a loopback address the link is omitted. Posting a message can never fail or delay a deploy. Anything that goes wrong is written into the run log as a # telegram: line and otherwise ignored. The final message is retried once; the started message is not, since the final one supersedes it minutes later anyway.

The bot token lives in config.json alongside the other secrets, in a file webhookr keeps owner-only.

Token verify mode

For non-GitHub senders, set the project's verify_mode to token (webhookr add --verify-mode token, or webhookr edit --verify-mode token) and send the secret in a header:

X-Webhookr-Key: <secret>

Any POST to the hook URL carrying the correct X-Webhookr-Key header triggers the deploy. For a project with extra branches, add ?branch=<name> to deploy a branch other than the primary (see Multi-branch deploys).

Cloudflare Tunnel

Choose Cloudflare tunnel on the main screen, or run:

export CLOUDFLARE_API_TOKEN='scoped-token'
webhookr cloudflare --hostname hooks.example.com
sudo systemctl restart webhookr

The token needs Zone Read, DNS Write, and Cloudflare Tunnel Write for the target account/zone. webhookr uses it once to create or update a remotely managed tunnel, its ingress rule, and a proxied CNAME. The API token is not stored; only the narrower runtime tunnel token is saved to ~/.config/webhookr/cloudflare-credentials.json with owner-only permissions.

At runtime webhookr starts an installed cloudflared binary, or falls back to the official cloudflare/cloudflared Docker image with host networking. Restart the daemon after changing tunnel configuration. The public webhook URL becomes https://hooks.example.com/hooks/<id>.

To also publish the admin UI, see Web admin UI.

Files

  • Config: ~/.config/webhookr/config.json on Linux (override with WEBHOOKR_CONFIG or WEBHOOKR_CONFIG_DIR).
  • Logs / run history: ~/.local/share/webhookr/ on Linux (override with WEBHOOKR_STATE_DIR). Per-run logs live under ~/.local/share/webhookr/logs/runs/<run-id>.log, indexed by ~/.local/share/webhookr/runs.json.
  • Database backups: ~/.local/share/webhookr/backups/<project>/ when backups are on, pruned past the project's keep count.

Deploying with systemd

The install one-liner already sets up the service. To build and install from a checkout instead:

./deploy/install.sh

The script builds the release binary, installs it to /usr/local/bin/webhookr, installs the webhookr.service unit, and enables/starts it. The daemon runs in the foreground under systemd with Restart=always. Before starting, edit deploy/webhookr.service to uncomment and set User=/Group= to the account that owns the project checkouts (they must be writable by that user).
